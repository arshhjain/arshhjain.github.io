DWG 001.0

Why

Requirements · traceability

School maths has Khan Academy, where every topic maps to a lesson and a progress tick. My degree has 80-slide PDFs.

Nothing like that exists for the lecture decks an AI/ML course actually runs on. So I built the part I could: drop in any lecture and get back a topic map you can tick off, with a resource behind every node.

It started as a CLI on my laptop (PyPDF2, EasyOCR, Gemini 1.5 Flash) and grew into the Sopra Steria internship build. Once other students were uploading the same decks, three more requirements showed up on their own.

DWG 001.1

System map

FastAPI · SQLite · sentence-transformers · Gemini
DWG 001.2

Recall

REQ-02 · semantic cache · storage

The expensive call is Gemini, and everything else in the system exists so I get to skip it.

The extracted text gets embedded once with all-MiniLM-L6-v2: 384 floats, normalised to unit length, so cosine similarity collapses to a dot product. That vector gets compared against every stored document. If the nearest one scores ≥ 0.85, its stored analysis is served straight back and the UI says "Previously analyzed by a peer — served from cache".

A byte-exact hash would miss the same deck re-exported, re-spaced or with one typo fixed. Meaning doesn't change when whitespace does, so the cache keys on meaning.

SHA-256 is still there, but as the document's identity: it's what your mastery ticks are saved against. HOLD · tier count

  • Lookupsingle pass · linear scan over file_cache · O(n)
  • Hitserve stored JSON · register this upload under its own id
  • MissGemini → store {subject, tree, topics} + vector
DWG 001.3

Understand

REQ-01 · prompt contract · output shaping

The LLM doesn't get to be creative about format. It signs a contract.

The system prompt pins the output to one JSON shape: a subject and a nested topic tree. Then it fences the tree in:

  • Depthmax 3 levels
  • Names2–5 words each
  • Rootthe broadest concept the document covers
  • Scaleshort docs stay shallow; long docs go wide before deep
  • Guardnot academic → NON_ACADEMIC, shown as a polite refusal

Models still wrap JSON in markdown fences or add a chatty sentence. So the parser doesn't trust the edges: it slices from the first { to the last } and parses only that. The tree then gets flattened depth-first into a topic list for the rest of the pipeline.

DWG 001.4

Topic identity

REQ-03 · get_or_create_topic()

It's the same question as Recall, asked one level down, about a topic name instead of a whole lecture.

Every node in every tree passes through three gates. An exact name match reuses the row. Otherwise the name is embedded and compared against every stored topic, and a nearest neighbour at ≥ 0.65 gets its id reused. Only if both gates miss does a new topic exist.

Each node then writes two rows: one linking it to this document (document_topics, unique per pair), and one timestamped topic_hits row. That hit log is everything the community layer runs on.

Older topic rows without a vector get one backfilled the first time they're touched. Nothing needs a migration night.

DWG 001.5

Community decay

REQ-04 · get_community_topics()

A hit from today counts as 1. A hit from a week ago counts as about half.

A raw hit count is an all-time leaderboard, and the topic that was hot in August would sit on top forever. So each hit decays exponentially with age and the topic's score is the sum:

score = Σ e−0.1 · Δdays  ·  t½ = ln 2 / 0.1 ≈ 6.9 days

This is why steady beats spiky. Five days of one hit each outranks a ten-hit burst from three weeks ago. You can test it on the right: click a lane to add a hit, click a hit to remove it.

Top 20 by score make the Community tab. That same ranking also decides which topics the background loop resolves resources for first, so popular topics get fixed sooner.

DWG 001.6

Content Constitution

REQ-05 · resource_finder · background_jobs

YouTube's top result for a topic is whoever won the algorithm that week, not the source faculty would recommend.

The Constitution is a table of faculty rules: a subject, the rule, and the source they trust. Each rule is embedded when it's added, through a small CLI. When a topic needs a resource, it's matched against every rule.

If the best rule scores ≥ 0.45, the search is scoped to that source: topic + source_name. If it doesn't, the search falls back to topic + "university lecture". The scraper reads YouTube's ytInitialData and keeps the first real video.

None of this runs during your upload. A background loop picks the top-20 trending topics that still have no resource and resolves them three at a time on a thread pool, so the event loop stays free for requests. How often it wakes up depends on traffic.

DWG 001.7

Thresholds

One model · three decisions

The same 384-d embedding gets used three times, and each use sets the bar at a different height.

The bar sits where a false match costs the most. Serve the wrong lecture's map and a student studies the wrong thing, so recall is strictest at 0.85. Merge two topics that shouldn't be merged and the trending list is slightly off, so topic identity sits at 0.65. Scope a YouTube search to a source that's a loose fit and the worst case is a mildly worse video, so the Constitution is loosest at 0.45.

Drag the cursor and watch which of the three decisions flip.

DWG 001.8

Render & mastery

REQ-06 · vanilla JS · localStorage

The tree comes back as JSON and gets rendered recursively into cards you can tick off.

Ticks follow the tree in both directions. Ticking a parent ticks everything under it. Ticking the last open child ticks the parent. Unticking anything reopens its ancestors. The progress bar counts leaves only, so a big root tick doesn't inflate your progress.

Each tick is saved in localStorage under mastered:<sha-256>:<topic>, which is why the document needs a stable identity. Upload the same deck next month and your progress is still there. No account needed.

The upload view walks the same stages as the server (upload, extract, peer cache, analysis, resources) with an elapsed timer, so a 10-second Gemini call doesn't feel like a hang.

DWG 001.9

Fault tree

REQ-07 · every fallback in the repo

Every subsystem has a ladder. If the top rung breaks, you land on the next one. The bottom rung is the floor, and the floor is never a crash.

Click a rung to break it.

DWG 001.R

Revisions

Considered · paused · cut

The subset problem was the one I spent the most time on, and I chose not to ship it.

One student uploads a 10-chapter PDF. Another uploads 5 of those chapters. The whole-document vectors don't match, but every answer for those 5 chapters already exists.

The fix was chunk-level caching: page-level embeddings, or a chunk_cache table, with the tree stitched back together from cached pieces. It got too complicated, and it's an edge case where I couldn't make the result trustworthy without compromising somewhere else. A cache that sometimes serves a subtly wrong map is worse than one that sometimes costs a Gemini call.
